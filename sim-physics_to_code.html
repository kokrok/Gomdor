물리를 코드로 옮길 때 생기는 문제들

물리 법칙은 맞게 적었는데, 화면 속 공은 이상하게 움직일 때가 있다. 원인은 대부분 연속적인 시간을 잘게 끊어서 계산한다는 데 있다. 포물선 예제를 고치면서 실제로 만난 문제부터 하나씩 정리한다.

1. 최고점에서 멈추는 공 — 꿈틀이 방지의 함정

바닥에 거의 멈춘 공은 아주 작게 계속 튀면서 꿈틀거린다. 그래서 "속도가 충분히 작으면 0으로 만든다"는 코드를 흔히 넣는다.

// 포물선 예제의 원래 코드
if (Shell.y < 0) {
  Shell.y = 0;
  Shell.vy *= -bounce;
}
if (Math.abs(Shell.vy) < 0.2) {
  Shell.vy = 0;          // 꿈틀이 방지
}

문제는 이 검사가 바닥 밖에서, 매 프레임 실행된다는 점이다. 공을 위로 던지면 vy는 줄어들다가 최고점에서 0을 지난다. 그 순간 검사에 걸려 vy = 0이 된다. 다음 프레임에 중력 때문에 vy = −0.05가 되어도, 여전히 0.2보다 작으니 또 0이 된다. 결국 공은 최고점에 영원히 떠 있다.

물리로 말하면: "속도가 작다"는 조건은 정지해 있다는 뜻이 아니다. 최고점에서는 속도가 0이지만 가속도는 여전히 −g다. 정지는 바닥이 받쳐 줄 때만 일어난다.

고친 코드: 검사를 바닥 충돌 안으로 옮긴다.

if (Shell.y < 0) {
  Shell.y = 0;
  Shell.vy *= -bounce;
  if (Math.abs(Shell.vy) < 0.2) {
    Shell.vy = 0;        // 바닥에서 튈 때만
  }
}

🔬 체험 1: 세 가지 코드로 공을 던져 보기

①은 꼭대기에서 멈춘다. ②는 땅에 떨어지지만 튄 횟수가 끝없이 늘어난다 (아주 작게 튀어서 눈에는 거의 안 보인다). ③만 완전히 멈춘다. ②의 이유는 다음 절에서 본다.

2. 영원히 튀는 공 — 계산 순서와 에너지

1절을 고쳐도 공이 멈추지 않는다(체험 1의 ②). 원인은 위치와 속도를 갱신하는 순서다.

// A. 위치 먼저 (explicit Euler)        // B. 속도 먼저 (semi-implicit Euler)
y  += vy;                               vy += ay;
vy += ay;                               y  += vy;

두 줄의 순서만 다른데 결과가 다르다. 한 번 튀어 올랐다가 다시 바닥에 닿을 때의 속도를 계산해 보면 이유가 보인다. 속도 v로 튀어 오르고, 한 단계 시간을 h, 중력을 g라 하자.

방식 다시 바닥에 닿을 때의 속력 비행 한 번마다
A. 위치 먼저 v + g·h 에너지가 늘어난다
B. 속도 먼저 v − g·h 에너지가 줄어든다
실제 물리 v 그대로

A에서는 올라갈 때 위치 계산에 "중력이 아직 덜 작용한" 속도를 쓰기 때문에, 공이 조금씩 더 멀리 간다.

튈 때마다 반발계수 0.8만큼 속도가 줄지만, A는 착지할 때마다 g·h씩 다시 얻는다. 둘이 맞아떨어지는 속도가 있다.

v = 0.8 × (v + g·h)    →    v = 4·g·h = 4 × 0.05 = 0.2

이 속도가 꿈틀이 기준값 0.2와 같아서, 공은 기준선 바로 위에서 영원히 튄다. B는 비행할 때마다 오히려 손실이 생기므로 반드시 멈춘다.

체험 코너와 포물선 예제는 B(semi-implicit Euler)를 쓴다. 게임 엔진 대부분도 이 방식을 쓴다. C로 치면 for 루프 안의 두 줄 순서만 바꾼 것인데, 수치해석에서는 서로 다른 적분법이다.

3. 모니터마다 다른 속도 — 프레임 대신 실제 시간

requestAnimationFrame은 모니터 주사율에 맞춰 불린다. 60Hz 모니터에서는 1초에 60번, 144Hz에서는 144번이다. 매 프레임 vy -= 0.05를 하면 사실상 "1프레임 = 시간 1"로 계산하는 셈이라, 144Hz 모니터에서는 모든 것이 2.4배 빨라진다.

해결: 프레임 사이에 실제로 흐른 시간 dt를 재서 곱한다.

let lastTime = null;

function 프레임마다실행할거(now) {          // now: 브라우저가 넘겨주는 시각 (ms)
  requestAnimationFrame(프레임마다실행할거);
  if (lastTime === null) lastTime = now;
  let dt = Math.min((now - lastTime) / 1000, 0.05);  // 초 단위, 상한 0.05초
  lastTime = now;

  shell.vy += g * dt;       // v = v + a·dt
  shell.y  += shell.vy * dt; // x = x + v·dt
}
requestAnimationFrame(프레임마다실행할거);  // 직접 부르면 now가 undefined라서 rAF로 시작한다
  • 단위가 바뀐다: px/프레임 → px/s. 60fps 기준으로 환산하면 g = −0.05 × 60² = −180 px/s².
  • 상한(0.05초)이 필요한 이유: 다른 탭에 갔다 오면 rAF가 멈춰 있다가 dt가 수십 초로 튄다. 그러면 공이 한 번에 바닥을 뚫고 지나간다(5절 참고).
  • Python으로 치면 time.perf_counter()를 두 번 재서 뺀 값을 dt로 쓰는 것과 같다.

🔬 체험 2: 같은 공, 다른 주사율

가운데 공은 "1프레임 = 시간 1" 코드를 144Hz 화면에서 돌린 것이다. 혼자 2.4배 빠르다. 오른쪽은 같은 144Hz지만 dt를 써서 왼쪽(60Hz)과 같은 박자로 움직인다.

4. 바닥에 묻히는 공 — 중심과 표면

ctx.arc(x, y, radius, …)의 (x, y)는 원의 중심이다. 그런데 바닥 판정을 y < 0으로 하면, 공의 중심이 바닥에 닿을 때 튀므로 아래쪽 절반이 바닥에 묻힌다.

if (Shell.y < Shell.radius) {   // 아랫면(y − radius)이 바닥에 닿을 때
  Shell.y = Shell.radius;
  Shell.vy *= -bounce;
}

물리에서 질점(point mass)으로 계산하던 습관이 그대로 넘어온 경우다. 계산은 질점으로 해도 되지만, 충돌은 크기가 있는 물체의 표면에서 일어난다.

5. 벽을 뚫고 지나가는 공 — 터널링

준비 중. 한 단계에 움직이는 거리(v·dt)가 벽 두께보다 크면, 공이 벽 앞에서 벽 뒤로 "순간 이동"해서 충돌이 감지되지 않는다.
