Git 기초 — commit과 push는 다르다

커밋만으로는 GitHub에 올라가지 않는다. 커밋은 내 PC 안에 기록을 남기는 것이고, GitHub에 올리는 건 push라는 별도 단계다.

1. Git의 네 장소

① 작업 폴더
     │  git add
     ▼
② 스테이징
     │  git commit
     ▼
③ 내 PC 저장소      ← 여기까지는 인터넷 없이 내 PC 안에서
     │  git push
     ▼
④ GitHub

git pull: ④ GitHub → ③ 내 PC 저장소 → ① 작업 폴더 (받아와서 파일까지 바꿈)
장소 뜻
① 작업 폴더 파일을 고치는 곳 (VS Code에서 보이는 폴더)
② 스테이징 이번 커밋에 넣을 변경을 골라 두는 대기실
③ 내 PC 저장소 커밋 기록 보관소 (.git 폴더)
④ GitHub 인터넷에 있는 복사본 (원격 저장소, origin)
단계 명령 하는 일 인터넷 필요?
고치기 (에디터에서 저장) 파일 내용이 바뀜. Git은 아직 기록하지 않음 X
add git add 파일 "이번 커밋에 이 파일을 넣겠다"고 고르기 X
commit git commit -m "설명" 고른 변경을 하나의 기록(스냅숏) 으로 내 PC에 저장 X
push git push 내 PC의 커밋들을 GitHub에 올리기 O
pull git pull GitHub에 있는 새 커밋을 내 PC로 받아오기 O

.git 폴더가 ③ 내 PC 저장소다. 커밋 기록이 전부 이 안에 들어 있다.

비유

  • 게임 세이브: commit은 내 PC에 세이브 파일을 만드는 것, push는 그 세이브를 클라우드에 업로드하는 것. 세이브만 해 두면 다른 기기(모바일)에서는 볼 수 없다.
  • C 컴파일: 코드를 고치는 건 .c 파일 수정, commit은 그 상태를 버전으로 확정, push는 확정된 버전을 서버에 배포하는 것과 비슷하다.

2. 왜 commit과 push를 나눠 놨을까

  1. 인터넷 없이도 작업할 수 있다. 기차 안에서도 커밋을 여러 번 해 두고, 나중에 한 번에 push하면 된다.
  2. 올리기 전에 정리할 수 있다. 작은 커밋을 여러 개 쌓아 두고, 확인한 다음 올린다. 한번 올린 커밋은 다른 사람(다른 기기)이 받아 갔을 수 있어서 고치기가 까다롭다.
  3. 빠르고 안전하다. 커밋은 내 PC에서만 일어나서 순식간에 끝나고, 실수해도 GitHub에는 영향이 없다.

Google Drive, OneDrive와 다른 점: 그쪽은 저장하는 즉시 자동으로 올라가지만, Git은 "언제 올릴지"를 내가 정한다.

3. 브랜치(branch) — 커밋 기록의 갈래

실험하는 동안 main을 건드리지 않으려고 따로 길을 만든 것이다.

main         ●──●──●
                     \
menu-unify            ●──●──●──●──●──●   ← 새 기능을 작업한 커밋들
명령 하는 일
git switch -c 이름 새 브랜치를 만들고 그리로 이동
git switch main main 브랜치로 이동
git merge 이름 다른 브랜치의 커밋을 지금 브랜치에 합치기 (내 PC 안에서만)
git branch 브랜치 목록 보기
git branch -d 이름 다 쓴 브랜치 지우기 (합쳐진 경우만 지워짐)
  • merge도 내 PC 안에서만 일어난다. 합친 결과를 GitHub에 올리려면 역시 push가 필요하다.
  • 모바일 Claude가 만든 claude/... 브랜치도 같은 원리다. 모바일에서 브랜치를 만들어 작업하고 push까지 해 둬서 GitHub에 있었고, PC에서 그걸 받아 main에 합쳤다.

비유

  • Python 가상환경처럼, 본 환경(main)을 건드리지 않고 따로 실험하는 공간이다. 실험이 성공하면 합치고, 실패하면 버린다.

4. 자주 쓰는 확인 명령

명령 알려 주는 것
git status 지금 고친 파일, 커밋 안 한 변경, 현재 브랜치
git log --oneline 커밋 기록 한 줄씩
git diff 아직 커밋 안 한 변경 내용
git status -sb [ahead 3] = 아직 push 안 한 커밋 3개, [behind 2] = 아직 pull 안 한 커밋 2개

5. 하루 작업 흐름

git pull                         # ① 시작 전: 다른 기기에서 한 작업 받아오기
(파일 수정)
git add 파일들                    # ② 커밋할 파일 고르기
git commit -m "무엇을 왜 바꿨는지"  # ③ 내 PC에 기록
(②~③ 반복)
git push                         # ④ 끝날 때: GitHub에 올리기

PC와 모바일을 오가며 작업한다면 ① 시작 전 pull, ④ 끝날 때 push만 지켜도 충돌이 거의 없다.

6. GitHub Desktop 버튼과의 대응

GitHub Desktop Git 명령
왼쪽 아래 "Commit to main" git add + git commit
위쪽 "Push origin ↑3" git push (↑3 = 아직 안 올린 커밋 3개)
위쪽 "Fetch origin" git fetch (GitHub에 새 커밋이 있는지 확인만)
위쪽 "Pull origin ↓2" git pull (↓2 = 받아올 커밋 2개)
위쪽 "Current branch" git switch

7. 이 사이트(Gomdor)에서 겪은 일

  • OneDrive와 Git의 충돌: 프로젝트가 OneDrive 폴더 안에 있어서, OneDrive가 .git 안의 파일을 main - 복사본으로 복제해 git fetch가 고장 났다. 병합 도중 파일이 잠겨 빈 파일이 생긴 적도 있다. → Git 저장소는 OneDrive 밖에 두는 것이 좋다. 백업은 GitHub이 대신한다.
  • 23개 커밋 뒤처짐: 다른 기기에서 push한 작업을 PC에서 pull하지 않아서 생겼다. → 작업 시작 전 git pull.
